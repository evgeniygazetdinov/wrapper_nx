# Как копать MainThread через дизассемблер + лог

Минимальный рабочий план: найти точку краша внутри `MainThread()` в `libGame.so`, сопоставляя адреса из Ghidra/IDA с логами враппера и добавляя хуки на вызовы из MainThread.

---

## Как работает хук и для чего он нужен

### Что такое хук

**Хук** — это подмена вызова: когда код из `libGame.so` вызывает какую-то функцию (например, `OS_ScreenGetWidth` или `alSourcePlay`), мы подставляем **свою** функцию вместо оригинальной. Игра думает, что вызвала «систему», а на самом деле выполняется наш код.

В этом проекте хуки ставятся **по адрету функции в загруженном .so**: мы находим адрес символа (например, `_Z17OS_ScreenGetWidthv`) в памяти и **перезаписываем начало этой функции** так, чтобы при любом вызове управление сразу уходило в нашу функцию.

### Для чего нужны хуки

1. **Заглушить то, чего нет на Switch**  
   Игра вызывает Android/JNI, OpenGL-расширения, сервисы и т.п. На Switch этого нет — вызов привёл бы к крашу. Мы вешаем хук на такую функцию и в своей реализации просто возвращаем «безопасное» значение (0, false, пустая строка) и не вызываем оригинал.

2. **Подставить свою реализацию**  
   Вместо оригинальной логики мы делаем то, что нужно под платформу: например, `OS_ScreenGetWidth` возвращает наше `screen_width`, `WarGamepad_GetGamepadButtons` читает геймпад через libnx и т.д. Оригинальная функция из .so при этом не вызывается.

3. **Логирование и отладка**  
   Можно сделать обёртку: наша функция пишет в лог «enter»/«exit», потом вызывает **оригинал** (адрес которого мы сохранили до хука) и возвращает его результат. Так мы видим, какая функция вызывается и не падает ли внутри неё.

4. **Сузить место краша**  
   Вешая такие обёртки с логами на функции, которые вызывает `MainThread`, по последнему «enter» без «exit» понимаем, внутри какой функции происходит падение.

### Как это сделано технически (hook_arm64)

В `source/so_util.c`:

```c
void hook_arm64(uintptr_t addr, uintptr_t dst) {
  if (addr == 0) return;
  uint32_t *hook = (uint32_t *)addr;
  hook[0] = 0x58000051u; // LDR X17, #0x8   — загрузить адрес по (PC+8) в регистр X17
  hook[1] = 0xd61f0220u; // BR X17          — переход по адресу в X17
  *(uint64_t *)(hook + 2) = dst;            — по смещению +8 записан адрес нашей функции
}
```

- **addr** — адрес **начала** функции в `libGame.so` в памяти (его даёт `so_find_addr_safe("_Z17OS_ScreenGetWidthv")`).
- **dst** — адрес нашей функции (например, `OS_ScreenGetWidth` из `game.c`).

Что происходит:

1. Мы **перезаписываем** первые 16 байт кода по адресу `addr` (оригинальная функция в .so больше не выполняется с начала).
2. Туда кладём две инструкции AArch64: «загрузить в X17 значение по PC+8» и «перейти по X17».
3. По смещению +8 от начала записан 64-битный адрес `dst` — нашей функции.
4. Любой вызов этой функции из .so (например, `BL _Z17OS_ScreenGetWidthv`) теперь попадает по адресу `addr`, выполняет эти две инструкции и **сразу уходит** в нашу функцию. Возврат из нашей функции (RET) вернёт управление туда, откуда вызывали, как обычно.

Важно: после хука **оригинальный код функции в .so по адресу `addr` не выполняется**. Если нужно и логировать, и вызывать оригинал — мы сами сохраняем `addr` в переменную `real_Func` и из своей обёртки вызываем `real_Func(...)`.

### Где хуки ставятся в проекте

- **source/hooks/game.c** — `patch_game()`: хуки на OS/Android/файлы/геймпад/детали и т.д. (`so_find_addr_safe` + `hook_arm64`).
- **source/hooks/openal.c** — хуки на OpenAL (и заглушки, и подмена на свою реализацию).
- **source/hooks/opengl.c** — хуки на NVEventEGL* и т.п.

Хуки применяются **один раз** после загрузки и релокации .so, до вызова `so_execute_init_array` и `MainThread`. С этого момента все вызовы перехваченных символов идут в наш код.

## Предварительные условия

- **DEBUG_LOG 1** в `source/config.h` — иначе `debugPrintf` ничего не выводит.
- **nxlink** — запуск через netloader и приём логов в терминал.
- **libGame.so** — тот же бинарник, который реально грузится на Switch (из `build/` или с SD).
- **Ghidra** или **IDA** — для статического анализа (Ghidra бесплатен).

## Шаг 1. Логировать адрес MainThread в враппере

Чтобы сопоставить рантайм-адрес с Ghidra, нужно знать, по какому адресу реально загружена функция.

В `source/main.c`, перед вызовом `MainThread(NULL)`:

```c
if (MainThread) {
  debugPrintf("[main] MainThread = %p\n", (void *)MainThread);
  debugPrintf("[main] before MainThread()\n");
  MainThread(NULL);
  debugPrintf("[main] after MainThread()\n");
}
```

Пересобери, запусти через nxlink. В логе появится строка вида:

```text
[main] MainThread = 0x7ec7567124
```

Это **виртуальный адрес** функции в памяти процесса на Switch. Он будет равен `база загрузки .so + смещение функции в .text`. В Ghidra мы смотрим смещение; база загрузки у нас в логе как `load base = 0x...` (из `so_util`).

## Шаг 2. Открыть libGame.so в Ghidra (или IDA)

1. **Ghidra:** File → Import File → выбрать `build/libGame.so` (или путь к твоему `libGame.so`).
2. В мастере импорта:
   - Format: **ELF**
   - Language: **AARCH64:LE:64:default**
3. OK, дождаться автоанализа.
4. В окне **Symbol Tree** (слева) → **Functions** → поиск по имени.

В **IDA:** открыть тот же `libGame.so`, процессор AArch64, после загрузки искать функцию по имени в списке функций (Alt+T или поиск по имени).

## Шаг 3. Найти MainThread и сопоставить адреса

- **Имя символа в коде враппера:** `_Z10MainThreadPv` (C++ name mangling для `MainThread(void*)`).
- В Ghidra: в Symbol Tree ввести в поиск `MainThread` или `_Z10MainThreadPv`. Открыть функцию — Ghidra покажет её **адрес в образе** (например, `0x00123456`), это смещение относительно базы образа.
- В логе у тебя: `MainThread = 0x7ec7567124` и где-то выше `load base = 0x7ec7563000`. Тогда смещение в образе = `0x7124`. В Ghidra функция `_Z10MainThreadPv` должна начинаться с адреса `Image Base + 0x7124` (если Image Base = 0, то просто `0x7124`).

Так ты убеждаешься, что смотришь именно ту же функцию, что и вызывается на Switch.

---

## Шаг 4. Определить первые вызовы внутри MainThread

В Ghidra открой декомпилированный код (или листинг) функции `_Z10MainThreadPv`. В начале функции ищи вызовы других функций (в листинге — инструкции `BL` / `BLR`; в декомпиляторе — вызовы по имени или по адресу).

Выпиши **первые 5–10 вызываемых функций** (по имени символа или по смещению). Примеры того, что может быть:

- инициализация подсистем (аудио, графика, файлы);
- проверки окружения (JNI, Android API);
- загрузка конфига или ресурсов.

Цель — выбрать несколько кандидатов, которые вызываются **до ожидаемого места краша**. Их мы будем оборачивать логами через хуки.

Если имён нет — смотри адрес перехода (например, `BL sub_12345`). Адрес `sub_12345` в образе = смещение; по нему можно попробовать найти символ в том же .so (Ghidra → Search → For Strings / или поиск по адресу в Symbol Tree).

## Шаг 5. Добавить хук на одну из функций в game.c

Допустим, в Ghidra видно, что MainThread первым делом вызывает функцию с символом `_Z14SomeEngineInitv`. Тогда в нашем коде мы можем перехватить этот вызов и залогировать вход/выход.

1. В **source/hooks/game.c** объявить обёртку и указатель на оригинал:

```c
#include "../so_util.h"

static int (* real_SomeEngineInit)(void) = NULL;

static int my_SomeEngineInit(void) {
  debugPrintf("[hook] SomeEngineInit enter\n");
  int ret = 0;
  if (real_SomeEngineInit)
    ret = real_SomeEngineInit();
  debugPrintf("[hook] SomeEngineInit exit, ret=%d\n", ret);
  return ret;
}
```

2. В **patch_game()** в том же файле найти символ и подменить вызов:

```c
uintptr_t a = so_find_addr_safe("_Z14SomeEngineInitv");
if (a) {
  real_SomeEngineInit = (void *)a;  // сохранить оригинал, если нужен вызов
  hook_arm64(a, (uintptr_t)my_SomeEngineInit);
}
```

Если хочешь только логировать и не вызывать оригинал (чтобы проверить, не в нём ли краш):

```c
static int my_SomeEngineInit(void) {
  debugPrintf("[hook] SomeEngineInit called, skipping\n");
  return 0;  // заглушка
}
// в patch_game не сохранять real_*, а просто hook_arm64(a, (uintptr_t)my_SomeEngineInit);
```

3. Пересобрать, запустить через nxlink и посмотреть порядок логов: `[hook] ... enter` / `[hook] ... exit`.

---

## Шаг 6. Сузить место краша

- Если в логе есть `[hook] SomeEngineInit enter`, но нет `[hook] SomeEngineInit exit` — краш происходит **внутри** этой функции. Дальше можно открыть в Ghidra именно её и повторить процесс: найти её вызовы и повесить хуки на них.
- Если есть и enter, и exit по нескольким функциям подряд, а потом сразу `exiting ...` — значит, краш между последним «exit» и следующим вызовом. Добавь хук на следующую по порядку вызовов в MainThread (или внутри последней «без exit») и повтори.

Так шаг за шагом ты придёшь к конкретной функции/инструкции, после которой процесс завершается.

---

## Шаг 7. Решить: заглушить или патчить

- Если краш в вызове **Android/JNI** (например, получение класса, вызов метода) — у нас такого окружения нет; разумно такую функцию **заглушить** в хуке (не вызывать оригинал, вернуть безопасное значение или 0).
- Если краш в **нашей** уже перехваченной функции (например, работа с файлами, экраном) — смотреть реализацию заглушки в `game.c` и поправить её (пути, коды возврата, инициализация структур).
- Если нужно **пропустить только один вызов** внутри MainThread и при этом не трогать остальной код — в Ghidra/IDA можно сделать патч бинарника (заменить вызов на NOP или ветвление), но тогда придётся поддерживать патч при каждой смене `libGame.so`. Проще и безопаснее по возможности решать через хуки в враппере.

## Краткая справка

| Что | Где |
|-----|-----|
| Символ точки входа игры | `_Z10MainThreadPv` |
| Поиск адреса в .so | `so_find_addr_safe("_Z10MainThreadPv")` или `so_find_addr_rx_safe(...)` |
| Подмена вызова | `hook_arm64(addr, (uintptr_t)my_func)` в `patch_game()` |
| Лог в коде | `debugPrintf("[tag] message\n");` (работает только при `DEBUG_LOG 1`) |
| Адрес в логе | `[main] MainThread = 0x...` — виртуальный адрес в процессе |
| База загрузки .so | В логе: `load base = 0x...` (из so_util при загрузке) |

## Порядок работы (чеклист)

1. Включить `DEBUG_LOG 1`, пересобрать, запустить через nxlink — убедиться, что в логе есть `[main] MainThread = 0x...` и `load base = 0x...`.
2. Открыть тот же `libGame.so` в Ghidra, найти `_Z10MainThreadPv`, сверить смещение с логом.
3. В начале MainThread выписать несколько первых вызываемых функций (или адресов).
4. Для одной из них добавить хук в `game.c` (обёртка с `debugPrintf` enter/exit) и запись в `patch_game()`.
5. По логам определить, после какого вызова пропадает «exit» — это и есть функция краша.
6. Либо заглушить её в хуке, либо разобрать её в Ghidra и повторить шаги 4–5 для её внутренних вызовов.

После этого у тебя будет точное место падения и понятно, что заглушить или как поправить враппер.

Как копать MainThread через дизассемблер + лог
Распишу минимальный рабочий план, без лишней теории.
1. Найти MainThread в libGame.so (IDA / Ghidra)
Открываешь libGame.so в IDA или Ghidra (формат ELF, aarch64).
Ищешь символ по имени:
манглинг у нас в коде: _Z10MainThreadPv
в IDA: Shift+F12 (строки), потом Names; в Ghidra — Symbol Tree → Functions → поиск по имени.
Переходишь к функции _Z10MainThreadPv — это точка входа движка.
2. Привязать адрес к логам враппера
Мы уже берём адрес так:
void* (* MainThread)(void*) = (void *)so_find_addr_rx_safe("_Z10MainThreadPv");
Можешь добавить перед вызовом:
debugPrintf("[main] MainThread = %p\n", MainThread);debugPrintf("[main] calling MainThread()\n");MainThread(NULL);debugPrintf("[main] after MainThread()\n");
Адрес, который покажет лог (MainThread = 0x...), должен совпасть с адресом функции в IDA/Ghidra (с учётом базового смещения text_virtbase, если оно есть).
3. Поставить «мелкие» логи внутри MainThread без IDA‑патчей
Самый простой способ — обернуть MainThread в своей прокси‑функции:
static void *MainThread_trampoline(void *arg) {  debugPrintf("[MT] enter\n");  // сюда можно добавить проверки, лог текущих глобалок и т.п.  void *ret = real_MainThread(arg);  debugPrintf("[MT] exit, ret=%p\n", ret);  return ret;}
И в main.c сделать:
void* (* real_MainThread)(void*) = (void *)so_find_addr_rx_safe("_Z10MainThreadPv");void* (* MainThread)(void*) = MainThread_trampoline;
Но чтобы это сработало, нужно переписать адрес в таблице импорта / месте, откуда игра сама вызывает MainThread, а не только то, что мы вызываем из враппера. Это уже сложнее.
Практический лайфхак попроще:
В IDA/Ghidra смотри, какие явные функции вызываются в начале MainThread (что‑то вроде InitSomething, LoadConfig, CreateWindow, StartAudio).
Для любой такой функции Foo:
1) Найти её адрес через so_find_addr_rx_safe("...")
2) Обернуть её через наш хук в hooks/game.c (по аналогии с уже существующими хуками) и добавить debugPrintf до/после.
Так шаг за шагом ты сузишь место: по последнему хуку в логе будет видно, после какого вызова игра выпадает.
4. Когда пригодится прямой патч в IDA/Ghidra
Если окажется, что конкретный внутренний вызов в MainThread заведомо «андроидный» (например, лезет в Java/JNI или сервис, которого у нас нет), можно:
в IDA/Ghidra заменить этот вызов на NOP/прыжок дальше;
либо в враппере повесить хук на эту функцию и просто возвращать «успех» без реального действия.
Но прежде чем что‑то вырезать, критично важно локализовать конкретное место — для этого сейчас и нужны шаги 2–3: адреса + тонкие логи вокруг ключевых вызовов.

Коротко: «живой» дебаг Switch через Ghidra — почти нереалистичен
У Ghidra есть свой удалённый дебаггер, но:
нет готового backend’а под Horizon OS / libnx;
на Switch нет gdbserver, ptrace, нормального доступа к процессу;
придётся самому писать агент/loader под Ghidra Debugger API, что сильно сложнее всего остального.
Поэтому в реальных портах под Switch Ghidra используют как статический анализатор, а рантайм‑отладку делают:
через nxlink + логи (debugPrintf);
иногда через собственные «пробные» патчи в .so (NOP/ветвления, проверки и т.п.).
Ниже — как настроить Ghidra для удобной статики по твоему libGame.so, чтобы связать её с логами, а не про «attach к процессу».
1. Открыть libGame.so в Ghidra
Запусти Ghidra → создаёшь New Project (Non-Shared).
File → Import File… → выбираешь build/libGame.so.
В мастере импорта:
Format: ELF
Language: AARCH64:LE:64:default (или AARCH64 little‑endian).
Жми OK, соглашайся на авто‑анализ.
2. Привязать адреса из логов
В логе ты уже видишь:
[main] MainThread = 0x7ec756abcd  (пример)
Чтобы этот адрес совпал с тем, что в Ghidra:
В so_util.c посмотри, как считаются адреса:
   text_virtbase + sec_hdr[i].sh_addr
Обычно so_find_addr_rx_safe возвращает уже виртуальный адрес внутри процесса (то, что ты видишь в логе).
В Ghidra:
В окне Program Trees зайди в Memory → секция .text.
Смотри «Image Base» (обычно 0x0 или 0x100000).
Если в логах адреса сильно больше, это из‑за того, что мы мапим .so в большой виртуальный диапазон (пример: 0x7ec7563000 + offset).
Связка делается так:
В логе: MainThread = <addr_runtime>.
В Ghidra: функция _Z10MainThreadPv имеет адрес <image_base> + offset_in_text.
Разница между addr_runtime и offset_in_text даёт тебе text_virtbase, который ты можешь проверить или настроить в Ghidra (через Rebase Program), чтобы адреса логов и дизасма совпадали.
Практически: тебе достаточно найти _Z10MainThreadPv по имени, а потом уже смотреть её тело — даже если базовый адрес в рантайме сдвинут, структура кода та же.
3. Как использовать Ghidra вместе с логами
Реальный рабочий цикл такой:
В коде враппера логируешь адреса интересных функций:
   debugPrintf("[main] MainThread = %p\n", MainThread);
В Ghidra:
находишь _Z10MainThreadPv;
смотришь, какие функции она вызывает в начале (CALL/BL).
Для функций, которые вызываются рано (до ожидаемого падения), делаешь хуки/логи в своём коде:
   // hooks/game.c   void *(*real_SomeInit)(...) = NULL;   void *my_SomeInit(...) {     debugPrintf("[hook] SomeInit enter\n");     void *ret = real_SomeInit(...);     debugPrintf("[hook] SomeInit exit, ret=%p\n", ret);     return ret;   }
и в patch_game():
находишь адрес SomeInit через so_find_addr_rx_safe;
переписываешь его на my_SomeInit (по аналогии с уже существующими хуками).
Снова запускаешь через nxlink, смотришь логи:
по последнему «enter/exit» видно, после какого вызова игра вываливается;
в Ghidra можно увидеть, что эта функция делает, и принимать решение: заглушить, частично переписать, добавить окружение.

поставить брейкпоинты и «шагать» по коду в рантайме на Switch;
читать/писать память процесса по сети автоматически.
Для этого нужен свой сервер на консоли (по сути — mini‑gdbserver или кастом под Ghidra Debugger API). Это отдельный, довольно объёмный проект.
Если хочешь, следующим шагом могу:
подсказать конкретную точку входа MainThread в твоём libGame.so (какие функции видны в начале) и какую из них разумнее первой обернуть логами/хуком через hooks/game.c, чтобы не городить сложный удалённый дебаггер.
