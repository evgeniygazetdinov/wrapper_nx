# Разбор краша по дампу [fatal] в Ghidra

По логу nxlink после краша идёт блок `[fatal] *** EXCEPTION ***`. В ней по шагам расписано, что делать в Ghidra с таким логом.

---

## Краткий пошаговый мануал (дамп с повреждённым контекстом)

По твоему текущему дампу — что смотреть в Ghidra:

| Шаг | Действие |
|-----|----------|
| 1 | Открыть **project.elf** в Ghidra (или project_ghidra.elf, см. раздел 0). |
| 2 | **Window → Memory Map** → у сегмента с кодом выставить **Base Address** = `0x603320000` (NRO_base_approx из лога). |
| 3 | **Search → Memory** (Ctrl+Shift+E) → ввести `0x1232f80` (FAR из лога). Перейти по адресу. |
| 4 | Посмотреть, что за секция/данные по этому адресу в project.elf. |
| 5 | **Search → For References to** этот адрес — кто по нему обращается (если ссылки найдутся). |
| 6 | **PC** и **LR** (`0x600000002`, `0x600000000`) в этом дампе не использовать — контекст повреждён, по ним в NRO ничего не искать. |

Имеет смысл опираться на **FAR = 0x1232f80**: это адрес доступа при падении. Если в project.elf он не попадает в маппинг, ищи тот же адрес (или смещение от подходящей базы) в **libGame.so** или других загружаемых библиотеках.

### Подробнее: шаг 2 (Memory Map, Base Address)

Чтобы адреса в дампе (PC, LR, FAR) совпадали с адресами в листинге Ghidra, нужно задать тот же базовый адрес, что и у NRO в рантайме.

**Важно:** Не путай с просмотром кода. Если ты кликнул по `.text` в левой панели (Program Tree) — откроется листинг с дизассемблером (видны DWARF signatures, инструкции, комментарии вроде `ram:00100000-ram:005faa5f`). Это не то окно, где меняется база. Нужно открыть **Memory Map** — отдельное окно с таблицей блоков памяти.

1. В меню: **Window → Memory Map**.
2. Откроется окно со списком блоков памяти. В заголовке окна указан текущий Image Base (например `0x100000`).
3. В окне Memory Map найди действие **Set Image Base**:
   - Иконка в верхней панели окна Memory Map (над таблицей), либо
   - Правый клик по таблице блоков → **Set Image Base** в контекстном меню, либо
   - Меню окна Memory Map (если есть кнопка с ▼ рядом с иконками).
4. В диалоге введи новый Image Base: **`0x603320000`** (NRO_base_approx из твоего лога) → **OK**.
5. Все блоки памяти пересчитаются относительно новой базы; листинг обновится.

**Про FAR = 0x1232f80:** После смены базы на `0x603320000` весь наш NRO оказывается в диапазоне 0x603320000 и выше. Адрес `0x1232f80` меньше этой базы — значит он, скорее всего, **не из project.elf**, а из другой библиотеки (например libGame.so). Поиск по `0x1232f80` в project.elf может выдать «адрес вне загруженных блоков» — это нормально, тогда ищи в libGame.so. Если же FAR в твоём следующем дампе окажется больше NRO_base_approx, то поиск найдёт его в project.elf.

### Подробнее: шаг 3 (Search → Memory, переход по FAR)

Нужно перейти в программе по адресу сбоя (FAR), чтобы увидеть, какая секция или данные по этому адресу.

**Вызов диалога:**

1. В главном меню: **Search → Memory…** (или **Ctrl+Shift+E**).
2. Откроется окно поиска по памяти. В нём есть поле для ввода адреса (часто с подсказкой вроде «Address» или «Go to»).

**Ввод адреса:**

3. Введи **FAR** из лога. В твоём случае — **`0x1232f80`**. Можно писать `0x1232f80` или `1232f80` (Ghidra понимает hex; если поле показывает адреса как `00100000`, попробуй тот же формат: `001232f80`).
4. Нажми **Search**, **Go** или **OK** (или Enter). В некоторых версиях кнопка может называться «All» — тогда выбери поиск по адресу.

**Если адрес найден:**

5. Курсор в окне **Listing** (Code Browser) перейдёт на этот адрес. Листинг может показать:
   - **Код (инструкции)** — тогда это исполняемый код; смотри, какая инструкция (LDR, STR, LDP и т.п.) и какой регистр/смещение — это и есть «виновник» доступа.
   - **Данные** — сырые байты или уже распознанные типы (например `dd 0x...`, строка). Значит падение при доступе к данным; смотри контекст — рядом какие переменные или структуры.
6. В левой панели **Program Tree** проверь, в какой секции адрес: `.text`, `.data`, `.bss`, `.rodata`, `.got` и т.п. Это подскажет характер места (код, инициализированные данные, BSS, read-only, таблица переходов).
7. Обрати внимание на **символы/имена** рядом с адресом — Ghidra мог распознать метку; это сужает область поиска.

**Если адрес не найден:**

8. Ghidra может показать сообщение вроде «Address is not in a loaded memory block» или «No matching addresses». Это значит, что FAR **не в project.elf**, а в другом модуле.
9. Переходи к подразделу ниже: «FAR не найден в project.elf → ищем в libGame.so».

**Альтернатива:** можно попробовать **Navigation → Go To…** (или клавиша **G**) и ввести адрес — поведение похожее.

### FAR не найден в project.elf → ищем в libGame.so

FAR = **0x1232f80** — это **абсолютный runtime-адрес**: по нему процесс попытался обратиться к памяти и упал. Нам нужно понять, какой байт в libGame.so ему соответствует.

**Важно:** В Search → Memory всегда вводишь один и тот же FAR — **0x1232f80**. Меняется только **Image Base** у libGame.so, от него зависит, попадёт ли этот адрес в блоки.

| Действие | Что ввести | Пояснение |
|----------|------------|-----------|
| **1. Image Base для libGame.so** | **`0x0`** или **`00000000`** | Пробуем базу 0. Если загрузчик поставил libGame по адресу 0, то runtime 0x1232f80 = смещение 0x1232f80 в файле. |
| **2. Search → Memory** | **`0x1232f80`** или **`001232f80`** | Ищем тот же FAR — в Ghidra при базе 0 адреса совпадают с offset в файле. |

Если **адрес не найден** (не попал в блоки), значит libGame загрузилась с другой базы. Тогда пробуй:

| Image Base (Set Image Base) | Адрес для Search → Memory | Формула |
|----------------------------|---------------------------|---------|
| `0x1000000` (или `001000000`) | `0x232f80` | FAR − база = смещение в файле |
| `0x100000` | `0x132f80` | FAR − 0x100000 |
| `0x10000` | `0x1222f80` | FAR − 0x10000 |

**Формула:** `адрес для поиска = FAR − Image_Base`. Подбирай Image Base так, чтобы результат попал в диапазон блоков libGame (смотри **Window → Memory Map** — колонки Start/End).

**Проверка:** В Memory Map libGame посмотри самый большой блок (обычно .text). Если он, например, `0x0`–`0x1200000`, то 0x1232f80 уже за его пределами — значит, скорее всего, база не 0. Пробуй большие базы (0x1000000 и т.п.), чтобы FAR − база дало число меньше длины блока.

## 0. Если Ghidra пишет «Permission denied» на project.elf

Сборка в Docker создаёт артефакты от root; Ghidra (особенно из Snap) не открывает такие файлы.

**Варианты:**

- Открыть копию с твоим владельцем: в каталоге сборки выполнить  
  `cp project.elf project_ghidra.elf`  
  и в Ghidra открывать **project_ghidra.elf** (после каждой пересборки копию можно обновить той же командой).
- Либо после сборки выполнить:  
  `sudo chown $USER:$USER project.elf project.nro project.nacp`  
  и открывать сам **project.elf**.

---

## 1. Открыть project.elf в Ghidra

- **File → Import File** (или открыть существующий проект) → выбрать `project.elf` из каталога сборки.
- Дождаться анализа (Auto Analyze).

---

## 2. Задать Image Base под рантайм

В логе есть строка:
```text
[fatal] NRO_base_approx=0x603320000 (Image Base в Ghidra для project.elf)
```

- В Ghidra: **Window → Memory Map** (или двойной клик по программе в Program Tree).
- Выделить сегмент с кодом (обычно первый), **Edit** (или двойной клик).
- Поле **Base Address** поставить равным значению из лога: `0x603320000` (в твоём случае; при следующем краше возьми число из своего дампа).
- **Apply**, закрыть.

Так адреса в листинге Ghidra будут совпадать с адресами из дампа (PC, LR, FAR).

---

## 3. Два варианта лога

### Вариант A: В логе есть «LR_offset=0x... FAR_offset=0x...»

Значит LR и/или FAR попали в наш NRO, контекст более-менее адекватный.

- В логе будут строки вида:
  ```text
  [fatal] PC (faulting instruction) = 0x...
  [fatal] FAR (fault address)        = 0x...
  [fatal] LR_offset=0x...  FAR_offset=0x...
  ```
- В Ghidra (после установки Image Base из п.2):
  - **Search → Memory** (или Ctrl+Shift+E).
  - Ввести адрес **PC** из лога (faulting instruction) → перейти.
  - Либо ввести **LR** (адрес возврата) из строки `SP = ... LR = 0x...` — это код, который выполнялся до падения.
- Смотри функцию в листинге и дизассемблер: какая инструкция по PC, что за доступ по FAR (load/store).

---

### Вариант B: В логе «LR/FAR вне NRO (контекст повреждён...)»

Как в твоём примере: PC=0x600000002, SP=LR=0x600000000 (похоже на мусор), FAR=0x1232f80, смещения отрицательные (0xffff...).

В таком дампе по PC/LR в NRO смотреть нечего — контекст испорчен или краш в другом модуле.

Что делать:

1. **FAR = 0x1232f80** — адрес доступа, из-за которого падение (data abort). Его и имеет смысл искать.
2. В Ghidra **project.elf**:
   - Оставь Image Base как есть (или поставь 0).
   - **Search → Memory** → адрес **0x1232f80** (или тот FAR, что в твоём логе).
   - Если такой адрес есть в маппинге project.elf — посмотри, какая это секция/данные.
3. Искать **кто обращается к этому адресу**:
   - **Search → For References to** адрес FAR (если Ghidra его видит),
   - или по тексту/константам искать использование значения `0x1232f80` (или твоего FAR).
4. FAR может относиться к **другой библиотеке** (.so игры или либы вроде SDL/openal). Тогда:
   - открой соответствующий .so в отдельном проекте Ghidra,
   - задай в нём такой Image Base, чтобы адрес FAR попал в один из сегментов (подбор по типичным базам загрузки),
   - ищи в том .so код/данные по FAR.

---

## 4. Кратко по твоему конкретному логу

- **NRO_base_approx = 0x603320000** → в Memory Map для project.elf поставь Base = `0x603320000`.
- **PC = 0x600000002, LR = 0x600000000** — выглядят как битый контекст (круглые числа), по ним в NRO не ориентироваться.
- **FAR = 0x1232f80** — единственный правдоподобный адрес; в Ghidra ищи именно его (и ссылки на него), в project.elf или в .so/библиотеках, в зависимости от того, куда он попадёт в маппинге.

После правок в exception.c при «нормальном» краше в NRO в логе снова появятся положительные LR_offset/FAR_offset — тогда снова смотри п.3 вариант A.
